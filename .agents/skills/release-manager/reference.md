# Release manager — staging, secrets, dual record, version locations

## `.gitignore` and staging

- Read `.gitignore` (and `.git/info/exclude` if relevant) before recommending `git add`. This repo had no `.gitignore` when the skill was adapted, so check whether one exists now.
- Prefer **`git add -p`** or explicit paths: `git add path/to/file` instead of `git add .` when the tree is noisy (benchmark outputs, build directories, corpora).
- **`git add -n` / `git add --dry-run`** — Use to show what would be staged; catches accidental inclusion of build artifacts, corpora or local-only files.
- If `git status` shows **untracked** files that look like secrets or local config, do **not** stage them; warn the user.
- **`git add -f`** — Only if the user explicitly wants an ignored file committed (rare; require clear intent). The dual-record step below is the sole standing exception, and it force-adds into a *temporary index only*.

## Avoid committing secrets (heuristics)

Scan diffs and untracked files for patterns such as:

- Long base64 blobs, `BEGIN RSA PRIVATE KEY`, `BEGIN OPENSSH PRIVATE KEY`
- AWS-ish: `AKIA` access keys, `aws_secret_access_key`, `ASIA` session tokens
- High-entropy strings assigned to names like `password`, `secret`, `token`, `api_key`, `apikey`, `bearer`, `Authorization`
- `.env`, `.pem`, `.key`, `credentials.json`, `id_rsa` (often ignored — still verify nothing slipped in via force-add)
- Webhook URLs with embedded secrets, database URLs with passwords

**Corpora are a second class of leak.** This project benchmarks compression on real data (PCM audio, text, executables, already-compressed files). Never stage:

- large benchmark inputs or generated compressed outputs,
- files with unclear licensing or personal content (for example private recordings, emails, documents),
- anything that makes the repo heavy by accident.

Small synthetic fixtures generated by committed scripts and tiny public-domain test vectors are fine. Prefer committing a corpus *manifest* (names, sizes, checksums, source URLs) over the data itself.

If unsure, **stop** and ask the user to rotate, redact or exclude before committing.

## Dual-record commit (`serexpai-bmad`)

Purpose: every release lands twice — clean on the active branch, complete on the
append-only `serexpai-bmad` record branch (staged files **plus** all BMAD
modelling artifacts, including any gitignored `_bmad-output/`). Built entirely with
plumbing through a **temporary index**: no checkout, no stash, no branch switch,
working tree and real index untouched.

**Overlay paths** (adjust only by explicit user decision):
`_bmad-output/` (planning artifacts), `docs/decision_logs/`, `_bmad/`, `.agents/`.
If the user later adds other tool state (for example an autonomous-loop directory),
exclude its logs and live output files, and secret-scan the overlay before committing it.

```bash
# run AFTER the active-branch commit succeeds
ACTIVE=$(git rev-parse --abbrev-ref HEAD)
NEW=$(git rev-parse HEAD)                       # the just-made active-branch commit
TMP_INDEX=$(mktemp)

# 1) seed a throwaway index with the just-committed tree (= staged files, clean)
GIT_INDEX_FILE=$TMP_INDEX git read-tree "$NEW^{tree}"

# 2) overlay the modelling artifacts; -f is safe here — this index is discarded,
#    the active branch and real index never see these paths
GIT_INDEX_FILE=$TMP_INDEX git add -f _bmad-output/ docs/decision_logs/ _bmad/ .agents/ 2>/dev/null || true

# 3) write the tree, discard the index
TREE=$(GIT_INDEX_FILE=$TMP_INDEX git write-tree); rm -f "$TMP_INDEX"

# 4) commit with dual parents: prior record head (if any) + the paired code commit
MSG="bmad-record: <same subject as the paired commit>

Paired-With: $NEW ($ACTIVE)"
if git show-ref --quiet refs/heads/serexpai-bmad; then
  RECORD=$(echo "$MSG" | git commit-tree "$TREE" -p refs/heads/serexpai-bmad -p "$NEW" -F -)
else
  RECORD=$(echo "$MSG" | git commit-tree "$TREE" -p "$NEW" -F -)   # first record: branch born from the code commit
fi
git update-ref refs/heads/serexpai-bmad "$RECORD"
echo "record: $RECORD paired-with: $NEW"
```

**Rules:**

- The dual-parent shape is deliberate: `git log serexpai-bmad` interleaves the
  modelling record with the exact code commits each snapshot accompanied, and
  `git diff <record>^1 <record>` shows precisely what the overlay added.
- **Append-only**: never rebase, amend, cherry-pick onto, or force-push
  `serexpai-bmad`. A bad record is corrected by a new record.
- **Remote divergence**: once a remote exists, before appending run
  `git fetch origin serexpai-bmad` (ok if absent). If the local ref is behind,
  fast-forward it first; if *diverged* (records made on another machine), **stop
  and ask** — do not auto-merge records.
- Pushing (only on explicit order) pushes both: `git push origin "$ACTIVE" serexpai-bmad`.
- Never check out `serexpai-bmad` in this working copy to "fix" it — use plumbing
  or a separate worktree; a checkout would materialize ignored paths as tracked
  and confuse the primary working tree.
- If the tracked-everything choice was made (no `.gitignore` for BMAD paths), the
  overlay adds nothing beyond the code commit and the record is still created, so
  the record branch history stays continuous.
- Cursor runs shell commands in a sandbox that allows workspace writes; `mktemp`
  lands outside the workspace, so if the temp index cannot be created, retry with
  `TMP_INDEX=$(mktemp -p "$PWD/.git")` rather than dropping the record.

## Version locations

No version exists yet. Keep a single source of truth and sync the rest on every bump
(all must read the same string):

| File | Where |
|---|---|
| Language manifest **[TOOLCHAIN TBD]** (for example `Cargo.toml` or `pyproject.toml`) | `version` field |
| CLI source **[TOOLCHAIN TBD]** | `--version` output, ideally read from the manifest |
| `README.md` (when it exists) | version mention in the intro line |
| `docs/CHANGELOG.md` | new `## [x.y.z] - YYYY-MM-DD` section on a release cut |

Until a manifest exists, the changelog is the only version record.

Separate the **release version** from the **bitstream format version**. A release bump
does not change the bitstream version, and a bitstream change must be noted in the
changelog and in the format specification regardless of the release bump size.
